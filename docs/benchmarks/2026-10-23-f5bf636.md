# FastAPI-RS first-slice benchmark at `f5bf636`

## Result

The identity-checked first-slice gate passed all 15 selected observations.
In this direct-ASGI workload, FastAPI-RS was slower than FastAPI: median
latency was 1.237x and p95 latency was 1.454x the oracle. Sequential
request-loop throughput was 0.760x the oracle. This is one workload on one
host; it does not establish broad performance or full parity.

| Subject | Median | p95 | Samples | Sequential loop throughput |
| --- | ---: | ---: | ---: | ---: |
| FastAPI 0.157.0 | 133.375 µs | 155.291 µs | 1,000 | 7,136 req/s |
| FastAPI-RS | 164.979 µs | 225.833 µs | 1,000 | 5,426 req/s |
| Starlette control | 5.000 µs | 5.209 µs | 1,000 | 150,063 req/s |

The Starlette control is contextual. It does not implement FastAPI validation
or dependency behavior, so its latency is not subtracted from either FastAPI
result.

## Measurement boundary and limits

The workload is `fastapi.first-slice.valid-asgi`. Per-request latency measures
only `await app(scope, receive, send)`. It includes the FastAPI-RS public Python
facade, PyO3 conversion, Rust implementation, Pydantic work, and Starlette-RS
dispatch. It excludes process startup, app and route construction, ASGI scope
and callback creation, observation, loop bookkeeping, server work, and network
or HTTP-client overhead. Sequential loop throughput includes per-call setup,
response observation, correctness checks, and loop bookkeeping.

Each subject used 50 warmups and five rounds of 200 sequential samples. The
parity gate passed all 15 selected observations; untimed status, headers, and
body matched. The oracle and target both had `opentelemetry-api==1.44.0` and no
SDK or exporter. Telemetry behavior beyond this no-op environment is not
measured here.
